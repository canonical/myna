# Preface

Read this file before changing Myna Settings: the GTK application that onboards a machine, switches and configures inference backends, and edits the dictation settings the daemon reads live.

Read the top-level `.kb/agents.md` file before continuing below.

# Overview

Myna Settings is a host application, not a snap. It talks to snapd on the user's behalf and escalates to root through polkit for the few `snap` commands that need it, so it is packaged as a deb from `myna-config-deb/` and only shares the `myna-core` crate with the confined client. Every change applies the moment the user makes it, GNOME style, and the polkit prompt of the privilege it needs is the only confirmation: the user never sees a command. Activating a model's radio row on General switches to that model, and dismissing snapd's prompt silently puts the radio back on the connected model. A switch that does not take puts it back too, with a toast naming the model whose Details button opens the operation report; a successful one says nothing. A switch is a disconnect, a connect and a restart, each its own snapd change, so it first reads snapd's changes and changes nothing while snapd is changing Myna, the chosen model or the one it leaves, whose connect snapd would refuse after the disconnect had gone through; and one that fails or is cancelled after its disconnect connects the model it had again and restarts Myna on it (`active_backend::restore_lost_model`), so a switch never leaves the user with less than it found (#51). snapd lists a model's slot before its install is done, so a listed model whose install is still running shows the install's spinner and percentage on its row and its radio is insensitive until it is done; every discovery reads snapd's changes once to follow such an install, started elsewhere or before the window last closed, so reopening Settings shows it on the row and under Install more models. The Model tab's rows behave the same way: a dropdown or a switch applies on change, an entry row on Enter or its apply button, never per keystroke, and each change is its own plan of exact commands (`backend_apply::prepare_change`) run through one `pkexec` prompt at most. A model or engine change ends with `modelctl prune-cache`, after the restart so the server has let go of them, which removes the components the new selection does not use instead of leaving gigabytes of GPU runtime on disk (#61). snapd's download cache keeps a pruned blob until its periodic cleanup, hours later, so switching back before then reinstalls it without a download, and the disk is freed only then; switching back later downloads it again. While it runs, the changed row shows the value it is changing to, a spinner and what the apply is doing (an entry row, having no subtitle, shows it at its end and hides its pencil), and every other row is insensitive, since `operation_gate.rs` admits one operation at a time. The changed row itself stays sensitive and only stops taking input (`can-target`, `can-focus`, busy to assistive technology), because an insensitive row dims its progress line to an unreadable contrast. A change that does not take puts the row back to what the model reads back, with a toast naming the setting whose Details button opens the report; a dismissed prompt (pkexec exit 126) puts it back silently, and a success says nothing. A single installed model that is already connected is a plain row with no radio, since there is nothing to choose; a single model that is not connected keeps its radio, because activating it is how the user connects it. The installed model recommended for the user's language (`client/.kb/model-recommendation.md`) sorts first and carries a pill naming why, "Best for" the language's endonym, or plain "Recommended" when the family does not cover it; the language is read off the main thread, so the list shows no pill until it arrives. Every row of a known family, here and in the dialog below, ends in a flat, dimmed button summarising its languages by endonym ("English, Deutsch +23"), the user's first; it has its own label child so GTK draws no dropdown arrow, since beside the combo rows an arrow reads as "pick this model's language". Its popover lists them all, filled down each column in rows of one height whatever the script (a homogeneous grid plus a CSS line height, since fallback fonts for Arabic or Myanmar are taller), with the user's highlighted and the rest by name. Every endonym carries a Pango language attribute so 粵語 and 日本語 take their own glyph forms whatever the UI language. Languages are never shown as flags. Below the list, Install more models opens a dialog of the known families (`myna_core::language::ModelFamily::ALL`) that are not installed, the recommended one first with its pill and each with its languages; each row says what it downloads, sized for the engine its install hook will pick (`onboarding::family_offer`), and ends in an install control (`ui/install_control.rs`): an Install button, then a spinner with snapd's download percentage, then an "Installed" check. It installs from edge through snapd's REST API as the user, one install at a time (`snap_install.rs`), and the install lives in `BackendUi`, not the dialog, so closing the dialog leaves it running and reopening shows it; while it runs, the button's second line says what is installing. A dismissed prompt puts the button back silently, a failure with a toast whose Details open the report, and a success says nothing: the model appears in the list. The button hides once every known family is installed. While the best family of all is not installed, the button carries a dimmed second line saying a better model for the user's language is available, also set as its accessible description; it goes once that family is installed. The window rediscovers each time it regains focus, so a model installed elsewhere appears on return; an open dialog keeps the families it opened with and marks each installed one, and only the user closes it (`docs/refresh-budget.md`). Each row's radio, or the plain row, carries its subtitle and the pill's text as its accessible description, because the subtitle relation libadwaita sets reads as empty through GTK 4.14's AT-SPI. The Spoken language row is built with General's GSettings rows (`Placement::ActiveModel` in `myna_settings.rs`) but shown on the Model tab, in a Language group below Overview that names the code format, only while the active backend's family takes it (`ModelFamily::takes_spoken_language`, Whisper alone: Parakeet and SenseVoice detect the language and ignore it); the Model tab keeps one page per backend and a rebuild refills it in place, so it keeps its scroll position, takes that one row back and hands focus back to the row that had it, the changed row once its change is done. "When to transcribe" shows the mode in force for the connected backend (`MynaSettingsController::shown_value`): the stored choice when the key holds a user value, else the backend's default through `myna_core::effective_mode`, re-resolved whenever the connected backend changes; only picking an option writes (`client/.kb/runtime-settings.md`). General reads Keyboard shortcut, Dictation, Model; the Dictation rows follow `DICTATION_ORDER` in `myna_settings.rs`, not the schema, whose keys Gio lists in no designed order, and a key missing from it lands after them. A row's widget follows the key's type: a boolean is a switch (Sounds on start, stop and error, after Indicator style), an enum a combo, a bounded integer a spin row, anything else an entry. Sound style, below the Sounds switch, is the one row with a control of its own: a Preview button (`sound_preview.rs`) that calls the daemon's `PreviewSounds`, since the cues are compiled into the daemon and the deb has none; it follows the Sounds switch's sensitivity, and a refusal (daemon not running, too old, dictating) is a toast. The main menu's Report an Issue (`win.report-issue`) opens `.github/ISSUE_TEMPLATE/report.yml` in the browser with the Diagnostics report prefilled through the URL (`diagnostics::issue_url`), so the user writes only what went wrong; the form itself asks for nothing else. A report past GitHub's URL limit is never shortened: it goes to the clipboard whole, a toast says so and the form's field asks for the paste. Diagnostics reads the machine, the daemon and gnome-shell on the blocking pool (`host_facts` in `backend_ui.rs`), with every non-quiet discovery and again for a report, because each may wait on D-Bus; the UI thread only formats what it last read. A report also reads every backend's snapshot (`report_text`): only the Diagnostics tab reads them otherwise, and a report sent from General said "Engine none selected" for a backend serving on its GPU engine (#49). Diagnostics lists the text-model snaps (`ConnectionSnapshot::text_offers`: the slots declaring `MYNA_ROLE=text` and any other non-speech provider `myna:backend` is connected to) under Text models, each with the models its installed components declare, read from `<mount root>/<snap>/components/<current revision>/*/myna-text-model.json`, and a status that is the daemon's own chain summary once connected. A model that is not connected keeps what it failed to answer as a Note on its own entry; Problems list only the connected models' failures, each naming its snap.

The Processing tab opens with a Steps group (`processing_steps.rs`, GTK-free, and `processing_ui.rs`): one switch row per step in stage order, generated from the merged plugin catalogs plus the client's own Fitted to the field, never from a compiled list, so a plugin's step needs no Settings change. Tidy and the rules behind it work with no snap installed. Translate is an expander row whose switch enables it and whose "Translate to" combo (searchable, the user's locale first, "not installed" marked on the languages whose models are missing) lists every target the catalogs can reach from the dictation language, directly or through English; a non-English dictation language is shown read-only under "From". Choosing a language writes `translate.to` and, when its model is missing, starts the install (`plugin_install`) on the same Install control as everywhere. A step the text at its position does not suit (Tidy for a French dictation, Translate to the dictation language, several dictation languages) is dimmed with its reason as subtitle and an insensitive switch, a distinct silent state; an enabled step whose model is missing says what it needs and its size with an Install button, and the chain behaves as if it were off. The group owns its page (`set_data`), so nothing else has to hold it. The rows read the enabled ids and parameters from the store (`GioClientSettings::steps`, the active chain plus `fit` for the fit switch, written whole by `set_steps` onto the active chain in one apply) and what the daemon offers from `InstalledSteps` every 5 s; a step off or unreported is judged from the catalog. The example line under the steps re-renders as the switches change, from static strings, with no model call. Chinese script is the client's own step, built in and in no catalog, in the target-language stage after Translate: an expander row whose switch stores the `script` step and whose "Write Chinese as" combo stores `script.mode` (simplified, traditional, Taiwan, Hong Kong; switching on picks the desktop locale's, an earlier choice outliving the switch). It is dimmed with "Applies when the text is Chinese" unless the text at its position is: the translation target when Translate runs, else the dictation language (several languages: applicable, the runtime only touches text with ideographs; an unset language: only on a Chinese desktop locale). Past dictations is an action row at the bottom of the page that pushes a sub-page (`past_dictations_ui.rs`): the Keep a record switch on top, an explanation in place of the list while it is off, then the record newest first. Each row is built lazily (a page of 20, a Show more row for the next, 1000 read at most) and has an Original / Result toggle that swaps the row's text between what was heard and what was typed; the list follows the record file through a monitor. Add step is the last row of the Steps group and pushes the catalog page (`step_catalog.rs`, GTK-free, and the same `StepsPage`): one expander row per catalog entry plus the built-in Fitted to the field and Chinese script, locale-relevant first (an entry's `locales`, else its input language; Chinese script for a Chinese locale), then stage order. A row shows the description and, opened, the example, the download size, the quality evidence (`quality.source`, or "Not measured on a benchmark yet" for a carried-over value) and the license, attribution and source link, all from the catalog schema; only curated entries are listed, uncurated ones too when Settings runs with `MYNA_LIST_UNCURATED=1` (development and the plugins E2E suite). Its control is Add (installed or built in; insensitive with the reason as subtitle when the text would not suit it), Added, or the install control: the same `start_install` as the inline Install, so one prompt, one progress, silent cancel and a Details toast; Install is insensitive while a dictation runs or another install does, and once the daemon offers the model the row becomes Add. Adding switches the step on, sets `translate.to` for a translation model when the dictation language is its input, and returns to the list. An installed entry's expanded row also has Remove this model, and a step row whose model is installed has a menu with Remove model: one snapd request as the user (`plugin_install::remove`, the same polkit action), refused while a dictation runs or another install or removal does. Removing never edits the stored steps: the step stays on, its row says "Needs the German model (24 MB)" with the inline Install, the Add step row of the same entry offers Install again, and the daemon, told `RescanModels`, types what it heard meanwhile. Diagnostics lists the license and credit each installed text model's manifest declares, so the MPL-2.0 attribution duty is met there. Above it a banner shows when the daemon's `ChainStatus` is `degraded` (a step has no installed model, named from `ChainMissingRequests` with its languages ("translation from English to Deutsch"), else from `ChainMissing`) or `restart` (a model was connected after the daemon started), and hides it for `ready` or a daemon too old to publish the properties (`chain_notice.rs`). It polls the bus every 5 s off the main thread while the window lives, is advice only and never blocks a dictation, and Diagnostics lists the same state under Processing.

# Important

- One user action costs at most one polkit prompt, onboarding's "Install all components" included: asked of snapd as the user, the flag, the installs and the backend connect are three snapd actions, each `auth_admin_keep` on its own, so the button runs them as root through one `pkexec myna-config --set-up` (below). Two privilege paths exist and they are not interchangeable. Backend switching (`connect`, `disconnect`) goes straight to `/run/snapd.socket` as the user and snapd asks polkit itself; its `auth_admin_keep` is per action, so every call in one operation must use the same snapd action. The daemon restart that follows goes through `systemctl --user`, which needs no authorization. Backend configuration (`snap run <backend>.modelctl ...`) runs as root through one `pkexec myna-config --apply-plan` invocation, whose prompt shows the message of the polkit action in `data/com.canonical.Myna.Config.policy`. That action is `auth_admin_keep` for the active session (any and inactive stay `auth_admin`), and pkexec's subject is this process, so changes made one after another within polkit's five minutes ask once. pkexec runs the running binary (`current_exe()`), so only the installed `/usr/bin/myna-config` gets that action; a tree build asks for `org.freedesktop.policykit.exec`, which is plain `auth_admin` and asks every time. Do not work around that for tree builds. Onboarding's set-up (`--set-up`, `onboarding::set_up_steps`) is the same executor with its own action, whose message says it sets Myna up, and its own allowlist: `snap set system experimental.user-daemons=true`, `snap install --edge` of `myna` or a known family's snap, and `snap connect myna:backend <family snap>:provider`, plus, for a text plugin, `snap install --edge <myna-text|myna-translation>+<model-component>...` (components always named: snapd installs every component of a store snap when none is) and `snap connect myna:backend <text snap>:provider`, nothing else. It connects the model it installs rather than trusting snapd's auto-connect, which a bare noble was seen to skip. Once authorized the executor is root, which this process cannot signal, so the apply has no deadline (a model download can take minutes) and the UI waits for and reports the real outcome. Do not route a new operation through `pkexec` when snapd's REST API can do it unprivileged within one prompt. A failure report names the failed step as what it was (`ports::FailedStep`): a command with its executable, arguments, exit status and stderr, a snapd request with its method, path and HTTP status, or a D-Bus call such as gnome-shell's `EnableExtension`. Never dress a REST or D-Bus call as a command. A one-line message follows `Message:` on its line; a longer one starts below it.
- Nothing shows a command to paste. The Diagnostics page sends a missing Myna or model to the wizard (`win.setup`), and the component step's one "Install all components" button runs whatever is missing in order (`onboarding::install_plan`, `docs/onboarding.md`): snapd's flag, the app, the model recommended for the user's language (`onboarding::model_offer`), the extension. Its extension step only ever enables the system copy gnome-shell lists, over the session bus, or lists one installed since login in the user's `enabled-extensions` for the next login, which the last step then tells the user to log out for; it never installs one, never flips the switch that turns all extensions on or off, and an extension out of reach is skipped silently. The flag, the missing snaps and the model's connect are one root set-up; the wizard reads snapd's in-progress changes meanwhile to name the snap installing and its download. Install more models still installs through snapd's REST API as the user (one action, one prompt); snapd answers a write only once its polkit prompt is answered, so a write waits `SnapdTimeouts::authorization`, not the per-request timeout. An install's change outlives any deadline (a GPU model is 4 GB), so it is followed with no timeout (`snap_install.rs`) and the component counts as missing until snapd is done with it.
- A Myna snap's install that snapd failed on a store answer that may change (`got unexpected HTTP status code` 408, 429 or 5xx, `snap_install::StoreError`) runs once more, in both paths: the REST install as the user and the root set-up's `snap install`, inside the same pkexec so no second prompt. Every such store error, retried or not, is one journal line starting `myna-config: store: ` with its status and URL (the executor's reach the journal through Settings, which logs them from its stderr): evidence of the store's availability against its status page.
- A content slot counts as a speech model when it is an `inference-provider` slot whose `provider.env` declares `MYNA_ROLE=speech`, or (with no `MYNA_ROLE`) one of a known family's snap or carrying `task: speech-to-text`, which only the fake backend carries because the store rejects the attribute (`domain::connection_snapshot_with_roles`). Connected `inference-provider` slots for text or LLM snaps (`MYNA_ROLE=text` such as `myna-text`, or unlabelled LLM snaps such as `gemma4`) are preserved in `ConnectionSnapshot::text_providers` when switching speech models; only connections to slots with another content id are strays that a switch disconnects.
- The `--apply-plan` and `--set-up` executor is the trust boundary. It accepts only operations matching the exact shapes the UI produces (`apply_plan.rs`, `system_configurator.rs`). Extend the whitelist deliberately and with a test; never pass free-form argv through it.
- Nothing runs through a shell. Build every subprocess as a `CommandRequest` and run it through the `CommandRunner` port so tests can substitute a fixture.
- Read what snapd knows from its REST API (`adapters/snapd_client.rs`), never from a `snap` table: snap translates `snap list` and `snap connections` headers from `LC_MESSAGES` or `LANG` and ignores `LC_ALL`, so on a Swedish desktop a parser of them found nothing installed. The `snap` CLI is left for `snap info`, whose keys it does not translate, and for `snap run` of a model's JSON-speaking control app. The e2e `localized` suite runs Settings in Swedish.
- Subprocess spawning is budgeted per refresh reason (`docs/refresh-budget.md`). A new `snap` read must fit the budget or change it explicitly.
- The Diagnostics page is built once and edited in place (`BackendUi::rebuild_diagnostics_page`), and only when its report differs from the one shown, so a focus rediscovery that found nothing new leaves the reader's scroll and selection alone, and one that changed a line replaces just that span of the text (`replace_changed_text`). Never replace the page to refresh it. snapd lists `/v2/snaps` in a different order on every read, which made every rediscovery look like a change and rebuilt the page each time the window regained focus (a right-click's popover does that); `SnapdReads::installed_snaps` therefore returns them sorted by name.
- The diagnostics page measures CPU clock under load and pressure stalls on every refresh (`docs/performance-warnings.md`). Verdicts are enums in `performance.rs`; wording lives in the presenter. A host the reader cannot understand must render as unknown, never as a warning.
- Domain and controller modules are GTK-free and tested headlessly. Keep GTK to `ui/`, `*_ui.rs`, and `app.rs`.
- Every user-visible string goes through gettext. A new file with such a string must be added to `po/POTFILES.in`. Adding or changing one requires `make i18n` and committing the template; `make check` fails while either drifts. A `// TRANSLATORS:` comment reaches the template only on the line directly above the line holding the gettext call, so bind a placeholder frame to a variable under its comment.
- Strict confinement was measured and rejected (`docs/confinement.md`). Do not reopen it without new evidence.
- The GSettings schema this application writes is owned by `client/data/` and shared with the daemon.
- The deb builds against each series' own GTK and libadwaita. Noble's 4.14 and 1.5 are the floor, and the main workshop's newer toolkit hides their bugs: an unscrolled page of wrapping labels overflows the window, a dialog with no focusable child never receives keys, a fixed-size dialog warns when its content grows, and removing the focused row focuses the next focusable one and scrolls to it, which is why a Model tab rebuild clears the focus first and restores it with the viewport's scroll-to-focus off. `make test-noble` runs this crate's suites there, and the startup and shortcut tests fail on any toolkit warning. CSS that GTK 4.14 cannot parse (colour functions such as `oklab(from ...)`, `color-mix()`, `@media`) goes in `data/appearance-gtk416.css`, which loads only from GTK 4.16; in `appearance.css` it is a parser warning on Noble.
- The dictation key is the desktop's custom shortcut, which this application writes through `myna_platform::activation::Activation` (GNOME: media-keys, `platform/gnome/activation.rs`; Xfce: xfconf, `platform/xfce/activation.rs`; Plasma: kglobalaccel, `platform/kde/activation.rs`), calling the daemon's `Toggle` over D-Bus; `docs/onboarding.md` records how GNOME treats it and how a key follows an older daemon.

Text plugins (`plugin_catalog.rs`, `plugin_install.rs`, GTK-free) install and remove model components of `myna-text` and `myna-translation` from the merged catalogs: one snapd request as the user (`POST /v2/snaps/<snap>` with `components`, one prompt) when the snap is installed and connected, else one root `--set-up` (`PkexecSystemConfigurator::set_up_plugin`) that installs the snap with its components and connects `myna:backend`, since sideloaded snaps never auto-connect (`.kb/plugins-snapd.md`). Nothing runs while the daemon's `State` is loading, recording, transcribing or finalizing. After snapd is done the daemon is told `RescanModels` and `InstalledSteps` is read until it offers (or stops offering) the models; a daemon that never says so leaves the outcome `Unconfirmed`, not failed. REST component installs fail for sideloaded snaps until store enablement.

# Architecture

Hexagonal. `ports.rs` declares the traits the application depends on (backend repository, system configurator, client settings). `adapters/` implements them against real snapd, `snap`, `pkexec` and Gio. The desktop is reached only through `myna-platform` contracts, built per `Profile` by `Platform` (`platform/mod.rs`): the shortcut control, the wizard and Diagnostics never name a desktop (`client/.kb/platform-layer.md`). `domain.rs`, `active_backend.rs`, `backend_apply.rs`, `onboarding.rs`, `snap_install.rs`, `shortcut.rs`, and `machine.rs` hold the pure decision logic. The `*_controller.rs` and `*_ui.rs` pairs bind that logic to GTK, and `operation_gate.rs` ensures one privileged operation runs at a time.

# Directory

- `build/` - Build logic outside cargo: the minimum `blueprint-compiler` version that `tests/` pulls in with `include!`, and the translation install the deb build runs.
- `src/adapters/` - snapd REST client, `snap` CLI repository, pkexec configurator, Gio settings.
- `src/platform/` - The composition root and the per-desktop backends: `gnome/` (media-keys shortcut, shell extension) `xfce/` (xfconf shortcut, IBus) and `kde/` (kglobalaccel shortcut, IBus via KWin); `host.rs` holds what Xfce and Plasma share, the HUD host's autostart entry included.
- `src/hud_host/` - The `myna-hud-host` binary's supervision policy (`machine.rs`, pure), launch resolution and GLib glue; the Xfce and Plasma counterpart of the shell extension's supervisor (`client/.kb/platform-layer.md`).
- `src/ui/` - One module per Blueprint template in `data/`.
- `src/bin/` - `myna-hud-host` (the deb ships it) and a test fixture that stands in for a real command runner.
- `data/` - Blueprint templates, CSS, desktop entry, polkit action, man page, gresource manifest.
- `docs/` - Decision records: confinement gate, onboarding flow, refresh budget, performance warnings.
- `po/` - gettext template and translator instructions.
- `tests/` - Contract tests per port and adapter. `snap_packaging.rs` covers the `myna.config` gsettings wrapper the snap ships, which is a shell script and not this application.
