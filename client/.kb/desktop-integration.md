# Preface

Read this document when changing desktop activation, focus handling, IBus injection, preedit, notifications, the session sounds, or the HUD.

Read the top-level `.kb/agents.md` file before continuing below.

# Architecture

`myna-desktop` composes three replaceable boundaries around the orchestrator:

- `Trigger` produces activation edges: every poke toggles. The desktop's custom shortcut (GNOME media-keys, Xfce xfconf, Plasma kglobalaccel) calls `com.canonical.Myna.Dictation.Toggle`; `myna.toggle` connects to the control socket instead, for shortcuts older Myna Settings wrote, and both feed one channel with one parity. A held key's repeats toggle nothing (below). Stdin is debug-only.
- `Injector` hands out one `Target` per utterance, the sole owner of the right to write into the focused application. The contract is `myna_platform::text_input` (`.kb/platform-layer.md`), and the controller names nothing else of text input: no IBus type, only the contract and the capabilities a backend reports. The production implementation is an IBus engine; tests use a mock that models the field it writes into.
- `Indicator` publishes dictation state. Notifications are the fallback, used only while no client is registered with the daemon (`RegisterClient`, any unique bus name, pruned when it vanishes). The host that will show the pill owns that registration, not just the HUD: the HUD needs seconds to start and register, so the host (the HUD host supervisor on Xfce and Plasma, the GNOME extension) registers the moment the daemon's name appears, before spawning the HUD, and unregisters when it gives up (exit 78, backoff budget spent, extension disabled, supervisor stopping); a restarted daemon starts with an empty registry and is registered with again. The HUD still registers itself, and a HUD that maps mid-dictation reflects the current `State` on connect. While the GNOME extension hosts the standalone `myna-hud` renderer; on X11 window managers the renderer hosts itself (`myna-hud --host x11`, `.kb/platform-layer.md`).
- The toast is one notification replaced in place and closed by id. A state whose text the live toast already shows sends nothing, unless it is an error, which the user may have closed: the controller publishes `Recording` again on `Loading` and `Ready`, and Plasma refuses an identical `Notify` in quick succession (`ExcessNotificationGeneration`). A refused `Notify` keeps the old id, so `Hidden` still closes that toast.

The key is a custom shortcut Myna Settings writes: GNOME media-keys, Xfce xfconf or a kglobalaccel command shortcut on Plasma (`myna-config/docs/onboarding.md`, `.kb/platform-layer.md`). The GlobalShortcuts portal was the packaged activation until 2026-10 and was removed with hold-to-talk: stacked and duplicate consent dialogs, consent and retry races, app id drift (`myna_myna` versus `.`), grants surviving `snap remove --purge`, grabs needing a re-login, and no GlobalShortcuts at all on Noble's portal. `Activation` is still published, always `control`, for Myna Settings releases that read it.

The controller acquires the target before capture, refuses known secure fields, starts capture on activation, and finalizes on release or focus loss. Text buffered when focus is lost is discarded rather than sent to a different target. One select loop covers the whole utterance, including the events still queued after the session future finishes, so a focus loss is always seen before the next queued segment is written; the trigger and stats arms shut off once the session ends, because an edge arriving then belongs to the next utterance. A write the target refuses because its lease is gone ends the utterance as well: nothing further is attempted, and because that text reached no field, the completion reports the loss rather than a clean insertion, whatever the transcript holds. An empty transcript after a focus loss reads the same way rather than as silence.

A capture fault mid-utterance does not end the utterance at the controller either. The orchestrator finishes the session with the audio it had already accepted and raises the device afterwards, so the controller sees `CaptureLost` while the transcript is still coming: it moves the indicator to finishing, since capture is over even though the utterance is not, inserts the committed text on `Done` without publishing a completion state, and lets the terminal `Error` show the failure. The HUD reads recording, finishing, error, and never shows the hidden or "No speech detected" completion on the way, which would claim a clean dictation a dead microphone did not give. A fault with nothing captured has no text to wait for and stays an immediate error.

A target writes under a lease minted before the engine switch and bound to the input context the daemon focuses the engine on. Focus leaving that context, focus reaching any other context, a newer lease, or release ends it. Until focus arrives, the lease ignores what the previous release is still delivering: its `FocusOut`, and the `FocusInId` on the daemon's fake context that follows every `FocusOut` (named by the client string `fake`, not by its path, which looks like any other). Neither can be this lease's, because the daemon sends no `FocusOut` before the first `FocusIn` of an activation and never relays a focus change it handled before our engine was attached; nothing orders their dispatch against the next mint, so ignoring them is what keeps a good press from reporting a focus loss or binding the fake context. Once the lease is focused, both end it, unless the focus left around an activation and comes back (below). The fake context also holds focus while a key grab does, so when an acquire sees it, the wait for the field stretches from `FOCUS_WAIT` (400 ms) to `FOCUS_BLIP_GRACE` (1 s), and an engine left on it is `NoTarget`: a start key held past 400 ms otherwise acquired nothing and its release ended the dictation. Commit and preedit refuse an ended lease, and a focus stream taken afterwards still reports the loss. `acquire` is all or nothing within one limit: the rollback restores whatever engine the connection displaced, so where it displaced none, `myna-stt` stays the global engine, IBus having no call to unset one. The displaced input method belongs to the connection, not to one utterance: an activation records the engine `GetGlobalEngine` named, unless that is already `myna-stt`, where an earlier activation is still standing and what it displaced is kept instead. `myna-stt` is never recorded as something to restore, by any path. Release retires the lease before restoring, whose switch focuses the engine out; the release that still held the field, or that merely lost focus, consumes the record, and a superseded one restores nothing, because the lease that displaced it in turn carries the responsibility on. A failed restore is not retried.

Another engine made global takes the lease away. `SetGlobalEngine` answering is no proof the switch stuck: GNOME Shell re-applies its input source on every new IBus daemon, so the first press after an IBus restart can race it, and the user may pick another source mid-dictation. The daemon then detaches our engine with nothing but a `FocusOut`, the call a focus blip makes, so the lease used to ride it out as one: commits returned `Ok` and reached nothing, and the release switched the user's new source back. So the target asks: `acquire` reads `GetGlobalEngine` once focus has settled, and so do every `commit` (before anything is held) and `release`. Another engine there at a commit or the release ends the lease as `FocusLost` and cancels the restore the connection owed. At acquire, before capture starts, the engine is claimed back once (`reclaims`): there the taker is nearly always the Shell's re-application, which would otherwise fail the press after every IBus restart. The claim back records the taker as the engine to restore, so the release hands back the latest source. A switch the daemon failed is claimed back only when another engine has become global since, polled for up to `FOCUS_WAIT`: the daemon cancels a switch ("Operation was cancelled") as soon as a newer one arrives but names the newer engine only once it is done. Taken again, the press fails as `FocusLost` and that engine stays. Mid-dictation and at release Myna never claims it back, since there it cannot tell the Shell from the user's choice. A Shell switch landing between the acquire's `GetGlobalEngine` and its own switch is not seen: that switch displaced an engine it never learnt of, and `myna-stt` stays global after the release. It asks rather than watching the daemon's `GlobalEngineChanged`: before 1.5.31 (noble ships 1.5.29) ibus-daemon sends its broadcasts from `org.freedesktop.IBus`, which is no unique name, and zbus 5.18 panics on such a sender in its connection task, which then answers nothing. The task checks every match rule against every message, and the object server registers one, so the injector's connection must never subscribe to a signal (no `AddMatch`, signal stream or property-caching proxy); `the_injector_outlives_the_daemons_broadcasts` fails on 1.5.29 if it does. A client reading such a message must not call `Message::header` either, which panics the same way: the gated suite parses the header from the raw bytes. Preedit is not checked: it is volatile, and into a detached engine it shows nowhere.

A focus blip around an activation is not a loss. On X11 a global key grab, the dictation shortcut's own, sends the focused window FocusOut on the key's press and FocusIn on its release, and GTK relays both to its input context, so a stop by key reaches the engine as `FocusOutId(field)`, `FocusInId(fake)`, `FocusOutId(fake)`, `FocusInId(field)`, with the Toggle arriving after the first. Measured on Xubuntu noble: FocusOut 3 ms after the press, FocusIn 6 ms after the release, the Toggle 5-9 ms after the FocusOut through gdbus and about 80 ms through `myna.toggle`. The controller calls `Target::activated` for every trigger edge it reads while a target is held; it knows nothing of grabs. A `FocusOut` sends the lease away. If an activation came within `ACTIVATION_WINDOW` (500 ms) either side of it, focus back on the same context within `FOCUS_BLIP_GRACE` (1 s) of the `FocusOut`, or of the last activation since, restores the lease; otherwise it is a loss once the window is over, whatever the context, even if focus came straight back, because an application with one context per window moves focus between its fields the same way. Focus on any other context ends it at once. Writes before the activation are held, returning `Ok` without waiting, since the controller's loop must stay free to read the Toggle; writes after it wait for focus; held text lands once focus is back and is dropped with the loss otherwise, which is always reported. Release waits for any held commits' blip to resolve and returns their delivery result before the controller publishes the completion state. The cost is that a plain loss is reported up to 500 ms late, with nothing written meanwhile. A key held down keeps its blip open, however long: its repeats are activations (below), each restarting the grace, so the grace lasts as long as the key is held plus 1 s. A start key does the same while the injector acquires: on the fake context `acquire` waits `FOCUS_BLIP_GRACE` from the press or the last activation, so the field is found at the key's release. With no repeats a fake context focused for 1 s is no field (`NoTarget`), as for a press with nothing focused. Real losses, with no activation around them, are reported as fast as before. The activations do not go through the controller, which may be blocked in a write or a release waiting out that very blip: the composition root hands the injector's `Activation` handle (`Injector::activation`) to the control trigger (`ControlTrigger::hear`), and every poke, a repeat too, signals it as it arrives, on the D-Bus or socket thread. `LazyInjector` forwards the handle to whichever backend it has connected; the IBus one marks the current lease, the one being acquired included. The controller still calls `Target::activated` for each edge it reads, the contract's form of the same news.

A held shortcut repeats. Both desktops run the command again on every key repeat: Xubuntu (delay 500 ms, 20/s) ran it 21 times for a 1.5 s hold, the first repeat reaching the daemon 574 ms after the press, and GNOME (delay 500 ms, every 30 ms) 35 times. xfsettingsd's grabber (libxfce4ui) has no repeat filter and xfconf no option for one. Plasma's kglobalaccel launches a command shortcut on the press only (one launch for a 1.5 s hold, KDE VM), so there the filter below never fires. So the control trigger tells repeats from presses by their rhythm: a poke within `REPEAT_QUIET` (800 ms) of the one before is a repeat when another follows it within `REPEAT_FOLLOW` (200 ms), and from then on every poke within `REPEAT_FOLLOW` of the one before is dropped as one of the stream. A poke with none following is a press, delivered 200 ms late. Plain dropping of everything within the quiet interval was tried first and failed the e2e suite: a stop pressed 650 ms after the start was lost, and on X11 its grab then read as a focus loss that dropped the tail. So did dropping everything within `REPEAT_QUIET` while a stream ran: a stop tapped 0.7 s after a 2 s hold was taken for a repeat. Repeats were measured at most 93 ms apart. Pokes are stamped with their gap to the one before as they arrive, counting those a full backlog drops, since the controller may not read them for a second; the decision lives in the trigger, not in a future, because the controller reads it inside a `select`. Limits: `REPEAT_QUIET` must outlast the repeat delay plus a command's start-up, so a delay set longer than about 750 ms toggles again; a hold released between the first and second repeat (a 50 ms window on Xubuntu) toggles twice; two presses under 200 ms apart count as a repeat.

The lease binds an input context, not an application. GNOME Shell may multiplex every application through a single IBus input context, which is unverified here; where it does, context identity discriminates nothing between applications and the protection rests on the Shell sending `FocusOut` as focus moves. The lease check narrows the hole rather than closing it in any case: between `commit` reading the lease and the daemon routing `CommitText` to whichever context is focused when it arrives, the window is bounded, not eliminated, because IBus offers no way to address a commit to one context.

The engine exposes `FocusId` and `ActiveSurroundingText` so ibus-daemon names the context in `FocusInId`/`FocusOutId`. The daemon reads both asynchronously when it first creates the engine and caches the answers for its lifetime, keyed by the engine's name, so the first activation after the daemon starts (every login) begins with a plain `FocusIn`. ibus 1.5.34 then re-sends that focus as `FocusInId`, which names the lease's context; noble's 1.5.29 does not, and names a context only at the next focus change. Started by key on X11, that first focus is the fake context the grab holds: 1.5.34 names it at once, 1.5.29 sends `FocusOutId(fake)`, `FocusInId(field)` at the key's release (traced on Xubuntu noble), which used to end the lease as a focus move. So an unnamed focus that turns out to be the fake context, or leaves, before anything was written sends the lease to `Left`: writes are held, the next field focused within `FOCUS_BLIP_GRACE` binds it as it would a pending lease, and none is a loss. Once text or a preedit went out, the unnamed focus was a field: turning out to be the fake context is a loss, and a `FocusOutId` names it, so it goes away as a named field does and a stop key's blip is ridden out (a plain `FocusOut` names nothing and is a loss). The cost: in that first dictation only, a user who moves focus to another field before anything is written dictates into the new one. A lease that sees no focus while acquiring ends at the next focus call. The engine interface is dispatched without per-call tasks: zbus spawns one per method call by default, and focus calls must apply in the order the daemon sent them. The factory and engine are served by the connection builder, which returns only once zbus's object server listens: served later with `ObjectServer::at`, a `CreateEngine` arriving first is dropped unanswered and the daemon fails `SetGlobalEngine` after its 15 s timeout, which every first acquire on a connection (after each IBus restart) risked.

`ActiveSurroundingText` is true, so on every focus the daemon asks the field for the text around its cursor (on GNOME Wayland the Shell answers from text-input-v3). The engine keeps only the character before the cursor, or before the selection a commit replaces, for the focused lease, and never logs the text. The first commit of a dictation gets a space after a character that wants one, so a second dictation does not run on from the first; there is none at a line start, after an opening bracket, before closing punctuation or next to Chinese, Japanese or Thai. A field that sends no surrounding text gets no space. A daemon that read `false` from an older Myna keeps that until it restarts, which a re-login does.

A field is secure when its purpose is PASSWORD or PIN, or its hints include HIDDEN_TEXT; the guard runs at acquire, at every commit and for preedit. `ContentType.purpose` also maps to `FieldPurpose` (`0 -> Plain`, `5 -> Url`, `6 -> Email`, `10 -> Terminal`, others `Other`) without desktop app-ID lists; into a `Terminal` target, both `CommitBuffer::flush_ready` (ahead of inter-commit spacing) and `Target::commit` fold control characters and Unicode line/paragraph separators to single spaces (`fold_control_chars`) so even deterministic layout breaks never run or join commands. ibus-daemon delivers content type only by setting the engine's write-only `ContentType (uu)` property, after FocusIn, and this holds on GNOME Wayland, where the Shell forwards text-input-v3 content type. GNOME has no PIN purpose mapping, so a PIN field arrives as purpose 0 with PRIVATE and HIDDEN_TEXT, which the HIDDEN_TEXT rule catches. PRIVATE alone is accepted because browsers set it on every private-window field. A backend that reports `secure_field_detection: Unknown` is dictated into anyway (decision D4), as an IBus field that sends no content type is; the controller's `dictates_into` is the one place that policy is set.

On Plasma Wayland the same engine works unchanged behind KWin: an application's text-input (v2 for Qt, v3 for GTK4) goes to KWin, KWin hands it over input-method-v1 to `ibus-ui-gtk3 --enable-wayland-im`, the input method kwinrc names, which is the IBus client. Measured on Kubuntu 26.04 (IBus 1.5.34~rc2): commit, preedit, surrounding text, focus loss and secure fields reach the engine from Qt line edits and text edits, Kate, Konsole and GTK4 entries; a Qt or GTK4 password field arrives as purpose PASSWORD, so no AT-SPI is involved (Plasma sets `QT_ACCESSIBILITY=1` and leaves the a11y bus disabled). Unless `use-system-keyboard-layout` is set, `ibus-wayland` types every key the engine declines through the global engine's layout, so `myna-stt` names none (`default`) and the user's keeps applying while a dictation runs. Three gaps are upstream, with no Myna workaround: Konsole (like VTE) sends no surrounding text, so a second dictation runs on without a space; KTextEditor (Kate, KWrite, KDevelop) reports its own preedit as surrounding text, so the first dictation on an empty line starts with a space; and ibus-daemon unsets a global engine from its registry (an XKB layout, Mozc) whenever a component a client registered goes away (`bus_ibus_impl_check_global_engine` looks only at registered engines), so every exit of Myna's daemon leaves IBus with no engine, or with `myna-stt` when Myna outlives another such client. If that happens while the panel is still handling the `GlobalEngineChanged` before it, the panel dereferences the missing engine and crashes, and KWin restarts it and the daemon within seconds. `the_ibus_backend_conforms` triggers exactly that on KWin's daemon (its fixture drops each injector as it closes the field), one more reason it runs only against a private one.

With a `processing-chain` other than `exact` chosen, a dictation is held back from the field instead of typed as it arrives, because IBus cannot change text once it is committed and a node of the chain may still want to. `draft::CommitPolicy` says how long text is held, and the user does not choose it: it follows from what the chain's nodes need to see at once (`pipeline::Needs`). `Streaming` for no nodes, `Horizon { sentences: 1 }` when a finished sentence is enough for every node: everything is typed but the last finished sentence and the one being said, so a long dictation reaches the field as it goes and each piece is processed on its own. `AtEnd` when a node needs the whole dictation; no node does yet. The policy is read at each press. Held text gets no preedit; the controller shows it through a `DraftView`, which the daemon implements as the `DraftText` and `DraftTail` bus properties, and the Shell extension draws them (`extensions/myna-shell/draft.js`). Its `PLACE` constant picks where: `'pill'` (the default) draws a bubble just above the HUD pill, centred on it, with a tail pointing at it, in the pill's own colour, growing out of the pill as the first words arrive and draining back into it as the text is typed; `'centre'` draws it in the middle of the screen, and `'caret'` next to the text caret, read from `Main.inputMethod`. The pill's frame comes from the host (`host.js`, `OverlayHost.pillRect`) and, with no pill hosted, the bubble stays where the pill sits rather than moving to the middle. Where it goes and where its tail goes are pure functions in `draftPlace.js`, tested in `test/`. The Shell turns animations off, and so does the bubble. Being the extension's, the bubble exists only where the extension runs: a KDE or Xfce session has no draft. Every commit passes through a `process::Processor` first; the daemon's is a `Pipeline` of steps, each a rule or a `Request` to a model by task, sent as one JSON line to the socket in `MYNA_TEXT_MODELS` (default `$XDG_RUNTIME_DIR/myna-text-models.sock`). The steps come from the chain the user picked under What Myna types on the Processing tab, a radio list where each chain carries a description and the same spoken sentence as it would be typed (`myna_settings::choice_detail`). A chain is `pipeline::Node`s in a row: `tidy` is `Node::Tidy` (`text.cleanup`, guarded by `Check::ConservativeEdit`) and `tidy-french` adds `Node::French` (`text.translate` from `en` to `fr`, a demonstration). The chains are an exclusive list, not switches that combine, so the user never has to work out what two steps do together; a node graph the user edits and saves as a chain is the intended successor, and the list is then the chains installed. The steps are read for each piece of text, so a change applies from the next one. Every `Step::Ask` output folds control characters and Unicode line/paragraph separators to single spaces before `Check::verdict`, protecting chat fields and non-VTE terminals even when the field reports `Plain`, while deterministic `Step::Rule` layout breaks reach `Plain` fields and are folded only at `Terminal` sinks. A model that is missing, late, or fails its check leaves the text as heard. The checks live in `process/check.rs` and hold whatever the model: `ConservativeEdit` lets a cleanup only drop, recase and repunctuate, its answer's words an in-order subsequence of what was said, at most half of it (rounded up, two words always allowed) dropped, no more than six words in a row, and never a lone `not`, `never`, `cannot` or `*n't` (inside a longer repair it may go: "Monday, no, Tuesday"); a word of the user's vocabulary may stand in for up to three heard words that start as it does ("my sequel" for MySQL). `Usable` guards rewrites and translations: a length within 0.25-4x of what was said, and outside translation no chat opening ("Sure", "Here is") that the speech did not open with. Tidy takes no written instruction: one would make it a rewrite. Why a step was skipped is a `history::Skip` code in the record and in the log, beside character counts, never a word of the text, the answer or the far side's error; Myna Settings words each code in the user's language, and a code it does not know reads as `Other`. Held text is written even when the session fails after hearing it, and discarded on focus loss like any buffered text. Nothing persists it unless `processing-history` is on: then each piece is appended, as heard and as typed, to the record `myna_core::history` names (beside the settings store, mode 600), which Myna Settings lists newest first under Past dictations on the Processing tab and can clear. An entry also says what made it, shown when its row is opened: the chain's nick, each step's task with the model that answered, how long it took and why its answer was not used if it was not (the `Pipeline` leaves that trace for the recorder after each piece), the speech model from the backend's `Capabilities.models` as of the last press, and the Myna version. The model socket's reply may carry `model` beside `text`; a far side that does not say leaves it out of the record. A line written before these were kept still reads. The list follows the file through a monitor, so it fills as the daemon records.

While the `sounds` setting is on, the session is heard as well as seen. `sound::Chiming` wraps the daemon's indicator and derives the cues from the states it is shown, so a cue can never disagree with the HUD: Start when listening begins, which is the press and not the model's `Ready`, since capture buffers the speech through a cold load (a press with no model to reach therefore chimes Start then Error), Stop once per session at the first of finishing (`Finalizing`) or the end (hidden, or a recoverable notice such as "No speech detected"), and Error on a critical error, even after Stop, but not for a repeat of the error already showing; a press refused before capture is an Error alone. The cues are Myna's own, seven sets of start, stop and error compiled into the daemon from `myna-desktop/sounds/<set>/` and synthesized by `dev/synth_cues.py`: `myna` (Bird) whistled chirps with an alarm churr for error, `tine` (Chime, the default) a struck bar by modal synthesis, `hum` (Voice) the rising "hm?", falling "mm-hm." and clipped "uh-uh" of spoken backchannels, `marimba` (Marimba) the first cues Myna shipped, `drop` (Water) water drops whose bubbles rise in pitch as real ones do, `radio` (Radio) a walkie-talkie's squelch, two-tone and roger beep, band-limited to 300 Hz - 3.4 kHz, with mistuned beating carriers for error, and `koto` (Strings) Karplus-Strong plucks with a sitar-bridge buzz for error. The `sound-set` setting picks one, read at each cue. Within a set, stop is 2 LU quieter than start and error 1 LU louder, matched by K-weighted loudness rather than peak (a test measures it: radio peaks well below the struck sets at the same loudness), and every error differs from its start and stop in register, roughness and rhythm. The marimba set was the only one at first and was briefly dropped: each note was cut off 90 ms before the clip ended while still ringing, a click in every cue. It returned with each note released to zero; its 220 Hz error still falls below what laptop speakers reproduce. Theme events were tried first and dropped: no freedesktop event means "listening", and `device-added`/`device-removed` read as a USB drive. Rising-for-on is the convention every dictation product shares. The clips must fade in and out to silence, as a clip that stops above zero clicks; a test pins it. `Player` decodes the Ogg Vorbis clip (`myna_audio::playback`, at most 3 s) and plays it through a native PipeWire output stream on a thread of its own, one cue at a time with a short backlog, and gives up shortly past the cue's length when nothing plays it. Native protocol clients are not subject to WirePlumber's snap audio policy, which only the pulse protocol labels, so the `pipewire` plug that captures also plays and no `audio-playback` plug is needed. A failed play is logged and dropped. The start cue plays as capture opens, so the microphone can hear it. `PreviewSounds` on the D-Bus interface plays a whole set (start, stop, error, 500 ms apart) on the same player thread for Myna Settings' Preview button: the cues live in the daemon, so it is the one that plays them, and it alone knows a session is under way, so it refuses from the press until the session ends (state other than idle, notice or error), as the microphone would dictate the preview. A second preview while one plays is refused rather than queued.

Toggle activation has no release edge, so the controller also ends a session by policy (`AutoStop`): after the user's silence timeout without sustained voice, measured in captured audio from the stats tap. It ends exactly like a release, plus the trigger-parity resync a focus loss needs. The debug stdin trigger runs with the policy off. There is no session length cap: a model with an input limit is the backend's to window.

On completion the controller classifies the input from the same tap (`input_quality`): a speech-band SNR under 10 dB raises the recoverable "Background noise is high" notice on every such session. An empty transcript keeps its own message. The threshold comes from mixing noise into LibriSpeech at known SNRs and transcribing with Parakeet and Whisper; an absolute floor limit was tried first and dropped, because AGC headsets broke it in both directions. The SNR is also published as `InputSnr` for Diagnostics. The remedy stays in the PipeWire graph.

A backend can serve worse than it should and say so: a progress `warning`, with a `warning_code` naming it (a GPU engine serving on the CPU because its driver did not load, or a model thrashing for memory). The orchestrator headlines it in the user's language from the code, or takes the server's text for a code it does not know, and emits `Warning`. The controller holds the utterance's first one and shows it as the completion notice, after "Focus lost" and "No speech detected" and ahead of the noise notice, since the condition outlasts the utterance. Once shown, that code is not shown again until the daemon restarts; a warning an empty utterance could not show waits for the next.

Committed segments may be coalesced before IBus insertion because rapid adjacent commits are not reliable across all targets. Natural whitespace from the backend is preserved; compatibility spacing is added only when neither boundary supplies whitespace.

The IBus target never sends a commit longer than 255 UTF-16 units: longer text goes out in pieces that end between words. Receivers read a commit into fixed buffers and drop what does not fit without a word: Qt under Wine holds 256 units (#73), Noosphere 0.4.1 holds 1024 bytes and types the first 256 of a commit. The compositor has a limit too: a Wayland message is at most 4096 bytes, and Mutter 51 (libwayland 1.26) given a commit of 4084 bytes or more disconnects the focused application, which dies with "Error reading events from display: Argument list too long"; 4083 bytes arrive whole. A long dictation committed at once, held or from a batch backend, did that.

Pieces are paced by the field, not by the clock. Mutter sends each commit's `done` from an idle (mutter#5087, open), so two commits it reads in one turn of its loop reach the application as two `commit_string` and one `done`, and the earlier is lost. Unloaded, Mutter 51 reads commits sent back to back in separate turns and all land (200 of 200); with the Shell stopped for 150 ms as they were sent, 25 of 30 pieces were lost back to back and 5 of 30 at 100 ms apart, so no fixed gap is safe. A field answers text it was given: GTK4 sends its surrounding text within 3 ms and its cursor location a frame later, Noosphere its cursor location twice. The engine counts both (`SetSurroundingText`, `SetCursorLocation`), and after each piece the target waits up to `ECHO_WAIT` (2 s) for the count to move, then until the field has been quiet for `ECHO_SETTLE` (30 ms), because a late answer to one piece would otherwise pass for the next one's; that cost a piece in 5 runs before the settle was added. With it, no piece was lost in 36 commits of 3000 bytes with the Shell stopped for 150 or 700 ms, into GTK4 and Noosphere. A field that has said nothing since it was focused gets its pieces `SILENT_GAP` (100 ms) apart. An XIM field gets them back to back as before: XIM passes through no text-input and ibus-x11 relays no answer. The lease is checked between pieces, so focus lost midway ends the commit as `FocusLost` with the earlier pieces in the field. A 1322-character dictation is six pieces and takes about 0.2 s. `dev/commit-rig/run.sh` reproduces all of it in a nested Shell; `ibus_hw` holds the daemon-level cases.

In streaming mode, unstable hypotheses may replace the target's preedit region when the injector supports it. Preedit is volatile, clears before commits and on cancellation, and follows the same secure-field and focus-loss guards as committed text. The IBus preedit carries one WHOLE hint over its length only once `FocusInId` has named a non-`gnome-shell` client (unnamed contexts and `gnome-shell`, which on Wayland fronts every application, get none): libibus 1.5.33 and 1.5.34 give it a floating attribute list that GJS sinks and IBus then frees, so a non-empty list corrupts the Shell's heap and eventually segfaults it (#18, fixed upstream in 1.5.35). An empty list takes the safe path; drop the exception once every supported series ships the fix.

## Why an input method, not emulated input

The cross-desktop direction for synthetic input is libei/libeis mediated by the
`org.freedesktop.portal.RemoteDesktop` portal, and Mutter already carries libei
support. But libei emulates a *device* - keycodes and pointer motion - while
dictation needs a semantic text commit. The difference is substantive, not
cosmetic:

- A keycode is not a character. It names a physical key position, and which
  character it produces is decided later by whatever xkb layout the *receiving*
  client has at delivery time. Emitting "ü", "€", or anything Cyrillic means
  finding a (keycode, modifier level) pair that maps to that keysym in the
  layout in force, and temporarily rewriting the keymap when none exists - the
  trick `wtype` and `ydotool` use. That races the user's own typing and layout
  switching, and per-window layouts make it unwinnable. A commit is a UTF-8
  string: layout never enters the picture.
- Modifier state is global and shared. Synthesising capitals or AltGr levels
  means pressing and releasing real modifiers on the seat, interleaved with
  whatever the user physically holds down. Lose that race and the text is
  delivered as accelerators; a sentence typed while Ctrl is latched is a run of
  commands, some destructive.
- Keystrokes get interpreted; commits get inserted. Every synthetic key
  traverses the app's key handling: autocomplete popups, type-ahead find, modal
  editors, key repeat, candidate windows. A 120-character utterance is 120
  opportunities to intercept, reorder, or transform it. A commit arrives on the
  text-input interface as one atomic string the widget inserts verbatim, and
  typically as a single undo step.
- Keycodes fight the user's real IME; a commit sits downstream of it. With a
  CJK or Hangul input method active, synthetic keys feed *its* composition
  engine, so "nihao" becomes a candidate lookup rather than text. Being an input
  method puts our output exactly where an IME's committed text goes, after
  composition, and makes handing focus back to the user's IME a protocol
  operation rather than a guess.
- Streaming ASR needs preedit, which only the IM path has. `text-input-v3`
  carries provisional preedit alongside commit, plus surrounding-text and
  delete-surrounding-text. That is the exact shape of incremental recognition:
  show the running hypothesis as styled preedit, replace it when the recogniser
  revises, commit once it is stable. Keycode emulation can only fake revision
  with backspaces, which is lossy against any field that reflows, autocorrects,
  or autocompletes underneath it.
- Delivery is scoped. The compositor routes a commit to the surface holding an
  active text-input, so it can only land somewhere that asked for text.
  Emulated keys go wherever focus happens to be at delivery, including a
  different window if focus moved mid-utterance.

There is no cross-desktop text-commit portal yet, so IBus stays the path on
GNOME, Xfce and Plasma (where KWin runs it as its input method), and
`input-method-v2` the wlroots path. The genuinely-unsettled question is
whether a portable IM/text-injection interface ever standardises; until then
`Injector` is the portability boundary and IBus is the shipping backend.

# Important

- Never inject unstable hypotheses with `CommitText`.
- Never inject into a known secure field or after focus has moved.
- Implement what ibus-daemon sets or reads on an engine as D-Bus properties, and check declarations against a real engine's introspection (e.g. `gdbus introspect --address "$(ibus address)"` on `ibus-engine-simple`): the daemon discards error replies, so a wrong declaration fails silently.
- Do not let the indicator or HUD take keyboard focus.
- Keep activation, injection, and indication behind mockable traits.
- Treat source and tests in `myna-desktop` as authoritative for IBus serialization details.
