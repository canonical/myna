# Preface

Read this before adding desktop-specific behaviour to any client process, writing a backend for a new desktop, or changing a contract in `myna-platform`.

Read the top-level `.kb/agents.md` file before continuing below.

# Overview

Myna's processes reach the desktop through one porting layer, shaped like Cobalt's Starboard. `myna-platform` is the contract crate: each module is a desktop-neutral operation set with its capability structs and error types, and nothing in it binds GTK, zbus, gio or a desktop service. Each desktop supplies a backend per module, in the crate of the process that runs it: the daemon's in `myna-desktop`, the HUD's in `myna-hud`, Myna Settings' in `myna-config`. The core of a process names a contract, never GNOME, IBus, Mutter, xfconf or X11.

The layer is being introduced in steps: the contracts exist and `text_input` is the one already used by its process; the other modules gain their backends and callers in later work, and until then the GNOME code paths they describe still run directly.

# Important

- Keep `myna-platform` free of internal and toolkit dependencies. A contract that needs a toolkit type is the wrong contract: pass plain data, a callback or a stream.
- Query capabilities, never assume them. A backend reports what it can do (`TextInputCapabilities`); the caller decides policy from that. A backend never decides policy, and wording for the user (headlines, translations) stays with the caller.
- Unknown sessions get `Profile::Generic`, never a desktop-specific profile.
- Every backend of a module, mocks included, runs that module's conformance suite. A gap a fixture cannot cover is asserted as such in its test, not skipped.

# Architecture

## Modules

- `session` - `Session { kind, desktop }` detected from an environment snapshot, and the `Profile` chosen from it.
- `text_input` - `Injector` hands out one `Target` per utterance; the target commits, shows preedit, reports the character before the cursor and focus loss, and releases. `Injector::activation` is a handle that tells the backend of the user's activation as it happens, a held key's repeats included, usable while it acquires. `TextInputCapabilities { preedit, surrounding_text, secure_field_detection }` is answered without a live field. Backends: IBus (`myna-desktop/src/inject/ibus.rs`), the mock. The names stay `Injector`, `Target` and `InjectError`: they carry no desktop and match the controller's vocabulary, so a rename would only churn call sites.
- `activation` - read, bind and clear Myna's toggle accelerator, list the shortcuts holding a key (reserved ones flagged), release a conflict, watch for changes. `Accelerator` is GTK accelerator syntax, which both GSettings media-keys and xfconf `xfce4-keyboard-shortcuts` store, with spelling-insensitive comparison. Backends: GNOME's media-keys custom shortcut, Xfce's xfconf `/commands/custom/<accelerator>` and Plasma's kglobalaccel command shortcut (Myna Settings, below).
- `appearance` - accent, reduced motion and high contrast as plain readings, watched through a callback that says whether readings are already current. Palette and fallback policy stay in the HUD. Backends: GNOME's and the GTK one for Xfce and everything else, in the HUD and in Myna Settings (below).
- `components` - the desktop pieces Myna needs outside its own processes (GNOME's shell extension; Xfce's status surface autostart entry and IBus as the active input method; IBus as KWin's input method on Plasma), each with a purpose and a status, and enabling one as far as Myna can without authorization. Backends: GNOME's shell extension, Xfce's IBus and autostart entry, and Plasma's IBus (Myna Settings, below).
- `status_surface` - pure placement: bottom-centre of the chosen monitor's work area, the monitor chosen by focus then pointer then primary, and the work area an X11 host derives from EWMH struts. It matches the GNOME extension's `place.js`; hosting the window is the backend's. Backends: the GNOME extension, and the HUD's own X11 host (below).
- `Subscription` - what a watch returns; dropping it ends the watch.

## The X11 status surface host

`myna-hud --host x11` (`myna-hud/src/host/x11.rs`) makes the HUD its own host, for Xfce's supervisor to start. It exits 78 without starting GTK when the session is Wayland, and pins GDK to X11 otherwise. GTK4 can neither type nor place a toplevel, so the host works on the XID over an x11rb connection of its own, and the window's map cycle calls it through `HudWindow::set_host`:

- Window type `_NET_WM_WINDOW_TYPE_NOTIFICATION`. In xfwm4 it is not `WINDOW_REGULAR_FOCUSABLE`, so it is never focused on map, and it stacks in the notification layer above panels and fullscreen windows. DOCK, mutter's choice, gets xfwm4's dock shadow drawn around the whole transparent window; UTILITY is focused on map.
- `_NET_WM_USER_TIME` 0 and no `WM_TAKE_FOCUS`, set once after realize: focus-stealing prevention and focus fallback skip the window too.
- Before every map the monitor is pinned (focus, pointer, primary), and the window is moved to its target with `PPosition` set, so the window manager maps it in place rather than placing it. GDK writes `WM_NORMAL_HINTS` without a position on every layout, including the one right after the map, which races the manager's read: the position is set again on `MapNotify`.
- After every map: `WM_HINTS` input false and `_NET_WM_STATE_STICKY` by client message. GDK rewrites `WM_HINTS` and `_NET_WM_STATE` on every map, so neither can be set ahead; skip-taskbar/pager are GDK's own hints. Click-through is the empty input region, set again on `MapNotify`: xfwm4 copies a client's input shape to its frame only on a ShapeNotify, so a frame made after GDK set the shape takes every click.
- Re-placed on `_NET_WORKAREA` changes, on the window's own resizes and, with the monitor re-chosen, on monitor changes. The work area is the monitor less the `_NET_WM_STRUT_PARTIAL` (or `_NET_WM_STRUT`) of every `_NET_CLIENT_LIST` window, since `_NET_WORKAREA` is one rectangle for all monitors. A DOCK-typed client along the monitor's bottom that claims no strut also lowers it by its height, shown or autohidden below the edge: Xubuntu's launcher hides intelligently and has none, as `place.js` does for dash-to-dock.

`tests/x11_host_e2e.rs` plays the window manager under Xvfb and checks what it sees at map request time. GNOME's hover fade to 20% is not ported.

## The Xfce supervisor

Xfce has no shell extension to start and stop the HUD, so `myna-hud-host` (`myna-config/src/hud_host/`, shipped in the myna-config deb at `/usr/libexec/myna-config`) does it, started by `/etc/xdg/autostart/com.canonical.Myna.HudHost.desktop` (`OnlyShowIn=XFCE;`; Xfce never activates `graphical-session.target`). It watches `com.canonical.Myna.Dictation` and runs `snap run myna.hud --host x11` (or `$MYNA_HUD_BINARY --host x11`) only while the name is owned: SIGTERM when it goes, SIGKILL after 3 s, so an idle HUD never blocks a snap refresh (issue #38). A crash backs off 0.5 s doubling to 30 s, more than five consecutive failures (a run of a minute resets the count) make it dormant until the daemon next restarts, and exit 78 ("this session cannot host me") ends hosting for the session. The host also holds a connection to the session's X display and exits, HUD first, when it closes: a logout leaves the lingering user manager and its bus running, so only the display says the session ended. `hud_host/machine.rs` is the pure policy, the same as `extensions/myna-shell/respawn.js`.

The supervisor also owns the "a pill is coming" registration: when the name appears it calls `RegisterClient` on the daemon (synchronously, so the daemon has it before the HUD starts) and only then spawns the HUD, and it calls `UnregisterClient` on exit 78, when it goes dormant and when it is stopped. Until something is registered the daemon answers a dictation with a notification toast, and the snap HUD takes about 4 s to register itself, so without this a dictation just after the daemon starts shows a toast, not the pill (measured on Xubuntu). The name vanishing needs no call: the registry dies with the daemon, and the host registers again when the name returns. A crashed supervisor is pruned by its unique name like any client. The GNOME extension does the same through `registration.js`.

## Myna Settings' backends

`myna-config/src/platform/` holds them and `Platform` (`platform/mod.rs`) is Settings' composition root: `Platform::current()` builds the activation and components backends of the process's `Profile` once, and the shortcut control, the wizard and Diagnostics take them from it. Probes and tests pass their own `Components` to the wizard and set `MYNA_PLATFORM=gnome` for the rest.

- GNOME: `GnomeActivation` (media-keys; a `-static` key is reserved, a conflict's holder is `schema path key accelerator`) and `GnomeComponents` (the shell extension, `ComponentStatus` mapped one to one from what gnome-shell and the disk say).
- Xfce activation: `XfconfActivation` over `org.xfce.Xfconf` with gio, synchronously. xfsettingsd stores no label, finds an entry by the spelling it was written with and honours `/commands/custom` only while `/commands/custom/override` is true, so Myna's entry is the one whose command `shortcut::is_toggle_command` recognises, and `bind` refuses (`Unavailable`) until xfsettingsd has adopted the custom tree. Conflicts are the other `/commands/custom` entries and the window manager's `/xfwm4/custom` ones (read from `default` while not customised, and then not releasable). Nothing is reserved.
- Xfce components: IBus (installed? the session's `GTK_IM_MODULE` and `XMODIFIERS` say ibus and `ibus-daemon` runs? `~/.xinputrc`?) and the HUD host's autostart entry, status only: `Active` while `myna-hud-host` runs, `NeedsRelogin` for an entry installed since login (see the supervisor below). Xubuntu does not install IBus and Settings never installs a package, so a missing IBus is `Unavailable`. An input method nothing can be typed through (not set up, `Unavailable`, or another one in its place, `Blocked(Incompatible)`: Myna types only through IBus) opens the wizard at startup, holds its component step and is a Diagnostics problem (`onboarding::input_method_holds`, shared by both); one not set up is in the step's install plan, for the other two the line under the step names the `ibus` package (the myna-config deb `Recommends` it) or says to choose IBus. A `Failed` IBus holds nothing (KWin restarts it). Every other desktop piece is optional in the wizard and Diagnostics names its state. Enabling IBus is `im-config -n ibus` (`-w` in im-config 1.x) for the user, which takes effect at the next login.
- KDE activation: `KglobalaccelActivation` (`platform/kde/activation.rs`) over `org.kde.kglobalaccel` (hosted by KWin on Plasma 6), synchronously, every call bounded at 2 s (`platform/dbus.rs`, shared with xfconf). The binding is a command shortcut, as Plasma's Shortcuts settings make under "Add Command": a desktop entry in `~/.local/share/applications` with `X-KDE-GlobalAccel-CommandShortcut=true`, whose file name is the kglobalaccel component and whose `_launch` action holds the key; kglobalaccel launches the entry. As on Xfce, Myna's binding is the component whose entry runs a command `is_toggle_command` recognises, so one made by hand counts and a bind replaces it. Measured on kglobalacceld 6.6.5, each shaping the code: a component keeps the entry it loaded until logout, so an edited `Exec` never runs and Myna names its entry after its command (`com.canonical.Myna.Toggle-<FNV-1a of the command>.desktop`); `doRegister` of `_launch` on a component it creates leaves an ungrabbed `_launch` that never fires, so Myna registers a placeholder action and unregisters it, as the settings do; kglobalaccel finds a new entry through KSycoca, which looks at the disk at most every 1.5 s, so registering retries for up to 3 s (the wizard's first bind failed on the VM without it); `setForeignShortcutKeys` silently drops a key another action holds, so `bind` reads the keys back and refuses; a key sequence of fewer than four ints aborts KWin (libKF6GlobalAccel's demarshaller, the whole compositor restarts), so every key goes as four. Keys are Qt codes (`platform/kde/keys.rs`, Super is Qt's Meta; Hyper, Meta, keypad and keys outside the table cannot be bound). Conflicts are `globalShortcutsByKey`, named by the action, or the application for a `_launch`; nothing is reserved, and `release` drops only that key from the holder. Clearing empties the keys and deletes Myna's entries from the user's directory; kglobalaccel drops a component whose entry is gone. The watch is `yourShortcutsChanged` (every key change through kglobalaccel, the settings' included) plus the user's applications directory, since removing a command in the settings changes only that. Proven against a stand-in kglobalaccel on a private bus that models those quirks (`tests/kglobalaccel_activation.rs`), and on the KDE VM.
- KDE components: IBus as KWin's input method (`platform/kde/components.rs`), sharing `platform/host.rs` (IBus installed?, the process scan, the XDG dirs) with Xfce's. On Wayland KWin, not the session environment, runs the input method: the `.desktop` file kwinrc's `[Wayland] InputMethod` names (user kwinrc over the system's), at once when it changes and at every login, so there is no `NeedsRelogin`. Not installed is `Unavailable`; kwinrc naming IBus is `Active` with `ibus-daemon` running, else `Failed` (KWin restarts a killed IBus within 3 s); kwinrc naming anything else (fcitx5, plasma-keyboard), or `fcitx5` running, is `Blocked(Incompatible)` and never switched; nothing named is `Inactive`, and enabling runs `ibus start --type kde-wayland` (10 s timeout), IBus's own way to write kwinrc and signal KWin (`org.kde.kconfig.notify`). The plain `ibus start` that IBus Preferences runs does not configure KWin on Plasma 6.7. Enabling never runs it while kwinrc already names IBus: then `ibus start` waits for a `VirtualKeyboard.availableChanged` that never comes (IBus 1.5.34). KWin routes every key through the input method's grab, so a stopped IBus stalls typing in every text field until it resumes. No status surface component yet.
- `myna-desktop --install-shortcut` and `myna.install-shortcut` stay GNOME's own (the Rust CLI now refuses elsewhere, below). Inside the snap gio writes to a keyfile, not dconf, so the daemon shells out to the host's `gsettings` (`dconf` in the snap's script) with `GSETTINGS_BACKEND` cleared; the Settings backend cannot be used there, and it is GNOME-only anyway.

## Appearance backends

Two per process, chosen by `Profile` (`Gnome`; `Xfce`, `Kde` and `Generic` share the GTK one). The HUD's are `myna-hud/src/appearance/{gnome,generic}.rs` over the probes in `probe.rs`; Settings' are `myna-config/src/platform/{gnome/appearance,appearance}.rs`, which read only motion and contrast.

- GNOME: libadwaita's accent then the theme's `@accent_bg_color`; `gtk-interface-reduced-motion` (GTK 4.22) else the inverted `enable-animations` key; Adw high contrast (Settings adds `org.gnome.desktop.a11y.interface high-contrast`). GSettings are watched, all of it behind schema checks, since a missing schema aborts the process.
- GTK (Xfce, KDE, Generic): no GSettings. xfsettingsd publishes any `/Net`, `/Xft` and `/Gtk` xfconf property as XSETTINGS, which GTK maps to `GtkSettings`; its defaults set `Net/ThemeName` but not `Net/EnableAnimations`, and it exports nothing for contrast or reduced motion. So reduced motion is the 4.22 property or a disabled `gtk-enable-animations`, high contrast is Adw's or a theme named `*HighContrast*`, and the accent is the theme's CSS or none (the HUD then draws Ubuntu orange). Watched through `GtkSettings` and `AdwStyleManager` notifies.
- The HUD's pill takes its backend from `appearance::for_profile`, with the profile `main` resolved (below). `is_high_contrast_theme`, the name test both GTK backends use, is in `myna-platform::appearance`.

`conformance::appearance` needs a display, so the backends run it under xvfb: `myna-hud/tests/appearance_conformance.rs` (`MYNA_HUD_GTK_TESTS`) and `platform::appearance::tests` in Settings (`MYNA_CONFIG_GTK_TESTS`). Neither GNOME rig can set contrast (libadwaita takes it from the portal), so that check is reported inapplicable there.

## Profile selection

A process resolves its `Profile` once, at its composition root, with `Profile::select(&SessionEnv::from_process())`. `XDG_CURRENT_DESKTOP` is split on `:` and its first entry Myna knows, case-insensitively, names the desktop. The session kind is Wayland when `WAYLAND_DISPLAY` names a live socket, X11 when only `DISPLAY` is set, and `XDG_SESSION_TYPE` only when neither is, as for a user service started before the session exported them. GNOME on either kind is `Gnome`; Xfce is `Xfce` except on Wayland, where its X11 status surface host cannot run, so it is `Generic`; KDE is `Kde` on Wayland only, Plasma on X11 (or of unknown kind) being `Generic`, best effort; anything else is `Generic`. Until its backends land `Kde` composes exactly what `Generic` does, but every `match` names it. `MYNA_PLATFORM=gnome|xfce|kde|generic` overrides detection for tests, and a value naming no profile is an error rather than a fallback.

## Composition roots

One per process, each resolving the `Profile` once and passing it down; no module reads the environment for the session itself.

- Myna Settings: `Platform::current()` (`myna-config/src/platform/mod.rs`) builds activation, components and appearance for the profile.
- HUD: `Platform::current()` (`myna-hud/src/platform.rs`) in `main` gives the `Session` and `Profile`; the profile goes to `HudWindow::new` and `Pill::new`, which build the appearance backend (it needs the pill's own widget, so `main` cannot). `--host x11` stays the explicit contract rather than defaulting on `Profile::Xfce`: GNOME's extension starts the HUD with no flag and must keep the externally hosted mode, and the Xfce supervisor passes the flag. The HUD is always started inside the session (gnome-shell's `Gio.SubprocessLauncher` and `myna-hud-host` inherit its environment, `snap run` passes `XDG_CURRENT_DESKTOP` through), so its own environment is a sound source.
- Daemon: `Platform` (`myna-desktop/src/platform.rs`) is built only by `--install-shortcut`, which the user runs in a terminal in the session. Nothing at startup is desktop-dependent: text input is IBus and the fallback indicator is freedesktop notifications on every profile. The snap's user service starts before the session exports `DISPLAY`, `XDG_SESSION_TYPE` and `XDG_CURRENT_DESKTOP` (measured on Xubuntu: absent from its environ), so the daemon must never resolve the session from its own environment at startup.
- The user manager's environment (`org.freedesktop.systemd1.Manager.Environment` on the session bus, or `systemctl --user show-environment`) does hold them once the session is up, but the snap cannot read it: measured in a confined `myna.hud` shell on Xubuntu, the call and `ListNames` are both AppArmor-denied, and the generated profiles of `myna.myna` carry no `systemd1` rule on any bus. Left, should the daemon ever need the session at runtime: `NameHasOwner` on the session bus is allowed (`org.gnome.Shell` against `org.xfce.SessionManager` names the desktop, not the kind), or ask an unconfined helper such as `myna-hud-host`. A pure parser of the manager's `KEY=VALUE` list was not added: with no consumer it would be dead code.

## Conformance

The `conformance` feature carries the suites (Starboard's NPLB). A suite takes a fixture that sets up a fresh backend and a scripted field, runs every check, panics on a violation and returns a `Report` of checks passed, checks whose field-level assertions the fixture could not observe, and checks the backend's capabilities make inapplicable. The text input suite covers commit delivery, no commit or preedit after focus loss, focus streams taken late, a superseded target, release then reacquire, a focus blip on the same field (out and straight back, as an X11 key grab makes it) not being a loss after `Target::activated` and being one without, a blip held 3 s with activations repeating not being a loss (fields `grab` and `ungrab`; the reference backend's flaw counts its grace from the grab), secure-field refusal where detection is `Supported` (at acquire, and for commit and preedit once a held field turns secure, within a bound, since a desktop may tell the backend late), preedit cleared by commit and by release, and preedit inert where unsupported. The activation suite covers a fresh desktop, bind read back, rebind replacing the binding, clear and bind keeping other shortcuts, conflicts across spellings (never Myna's own), release freeing only that key, reserved keys refusing release (inapplicable where the desktop has none), and a watch that hears Myna's writes and the desktop's until dropped; its fixture names two commands the backend reads back as Myna's. `myna-platform/tests/activation_conformance.rs` proves it on a reference desktop and one flaw at a time; GNOME runs it against a memory GSettings backend, Xfce against a stand-in xfconfd and KDE against a stand-in kglobalaccel, each on a private bus. `myna-platform/tests/text_input_conformance.rs` proves the suite itself: an in-memory reference backend with a visible field passes every check, and the same backend with one flaw at a time fails the check that names it; a new check starts as a flaw the suite does not yet reject. Every text input backend runs it with its field observed: `MockInjector` (`myna-desktop/tests/text_input_conformance.rs`), which models the field it writes into, and `IbusInjector` (`the_ibus_backend_conforms` in `myna-desktop/tests/ibus_hw.rs`, under `MYNA_IBUS_TESTS`) against a real input context. That fixture orders its look at the field behind a key event, whose reply travels daemon, engine and daemon again, so everything the engine sent before arrives first; a field without focus is only drained, as the daemon routes nothing to it. Its field is an IBus client of its own, so no compositor sits in the path: on Plasma, KWin's part (text-input to input-method-v1) is checked with real Qt, KDE and GTK4 fields instead (`.kb/desktop-integration.md`).

Backend-neutral invariants that are the caller's, not a backend's, are pinned in the controller's tests: buffered text is discarded on focus loss, a backend reporting no preedit is never asked to draw one, and the policy where `secure_field_detection` is `Unknown` (dictate anyway, decision D4) lives in one function, `dictates_into`.
