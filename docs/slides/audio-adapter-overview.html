The wider effort: offline dictation for Ubuntu Desktop

  • Myna is push-to-talk speech-to-text for Ubuntu Desktop (Wayland/GNOME first): hold a hotkey, speak, committed text lands in the focused app (UD129)
  • Local and private by design: inference via the Canonical Inference Snap, no cloud, no network needed, audio never persisted to disk
  • Explicit user control: capture only while the hotkey is held, visible activity indicator, secure fields blocked

  • The Audio Adapter is a Rust library that captures microphone audio and prepares it for STT inference
  • Its one known consumer is the Speech Controller — the API surface it uses is pinned in the contract and guarded by a dedicated consumer-scenario test

What the library does

  • Stateless primitives — the caller owns the dictation session; the library just does enumerate_nodes() → open_stream() → read() loop → close()
  • Capture from PipeWire (native, primary) or PulseAudio (fallback), any input node the server exposes — one stream per node, idempotent open
  • Convert anything the mic produces into one stable STT format (default 16 kHz / mono / S16LE) — server-side negotiation preferred, in-process resampling (rubato) as fallback
  • Optionally preprocess: RNNoise denoising, Silero voice-activity detection (feature-gated; dereverb deferred)

Streaming semantics: honest, artifact-free audio

SituationBehavior
Consumer reads too slowlyDrop oldest frames, emit Overrun event, smooth the splice
Audio server underrunsFill gap with silence (timeline stays continuous), emit Underrun, smoothed boundaries
Mic unplugged mid-streamDeviceLost error, stream closes — caller decides what's next
Source format changes mid-streamRenegotiate transparently; error only if unconvertible

Frames are contiguous and non-overlapping; bounded 10 s in-memory buffer; nothing ever written to disk. All of this is codified as 15 testable contract guarantees (G1–G15).

One dictation session, end to end

// settings time
let nodes = enumerate_nodes()?;            // populate device picker
// hotkey pressed
let mut stream = open_stream(&config)?;    // first frame ≤ 100 ms
while hotkey_held {
    for item in stream.read_timeout(d)? {
        match item {
            Frame(f)                  => inference.send(f.data),
            Event(VoiceActivity{..})  => chunk_utterance(),
            Event(DeviceLost{..})     => end_session_with_error(),
            Event(_)                  => log_diagnostics(),
        }
    }
}
// hotkey released
stream.close();                            // ≤ 200 ms, buffers cleared

This exact call pattern is the Speech Controller's consumer surface — asserted by tests/consumer_scenario.rs.

The constitution: non-negotiables

  • I Red-green TDD — tests written and observed failing before implementation
  • II Integration-ready — same tests run on a VM with a virtual audio interface or on real hardware
  • III Performance watermarks — checked-in high/low baselines (memory, CPU, latency) with tolerances that catch drift
  • IV Workshop environments — workshop.yaml defines the dev/test sandbox; no ad-hoc host setup
  • V Privacy-first — no audio on disk, no network, bounded buffers
  • Plus: staged feature-branch delivery, and concise unattributed commits/PRs

Testing regime

Three layers

  • Hermetic unit + contract tests (MockBackend, WAV fixtures)
  • Integration tests against a live server via virtual audio nodes
  • Conformance examples: first frame ≤ 100 ms, close ≤ 200 ms, lag ≤ 100 ms

Workshop sandbox

  • One command brings up an isolated audio server — PipeWire or PulseAudio, selected at launch
  • Per-backend declared test subsets; host audio never touched
  • Offline after first provisioning; environment errors ≠ test failures
